# Contract: AI/SDLC Readiness Check

Every item below traces to an `intent.md` goal (`G1`–`G7`) in its **Traces to** line.
This contract **extends** `specs/archived/readiness-doctor/contract.md`; every guarantee
it made that is not explicitly amended here continues to hold unchanged.

## Interfaces

### Public API — `src/doctor.ts`

Additive only. No exported symbol is removed or renamed; `DoctorOptions`,
`DoctorResult`, `runDoctor`, `buildDoctorFiles`, `DOCTOR_RUNNER_PATH`,
`DOCTOR_CHECKS_PATH`, `SPECS_DIR`, `RESERVED_SPEC_DIRS`, `SHIPPED_MARKER` and
`APPROVED_VERDICTS` keep their current shapes and values exactly.

```ts
/** Priority tier for a presence assertion. `must-have` (the default when the field is
 *  absent) fails the run and makes the repo report not ready; `recommended` warns —
 *  named in the report with its remediation, never changing an exit code.
 *
 *  Unrelated to `CostTier` in `src/vocabulary.ts`, which selects a model for a role.
 *  The two never meet; this type is owned here and never imported from there. */
export type CheckTier = 'must-have' | 'recommended';

export interface DoctorCheck {
  readonly id: string;
  readonly description: string;
  readonly anyOf: readonly string[];
  readonly remediation: string;
  readonly requires?: ToolProbe;
  /** **(NEW — ai-sdlc-readiness.)** Absent means `'must-have'`: every check written
   *  before this feature keeps its exact behavior, and a `checks.json` generated by an
   *  earlier harny still runs correctly against the new runner (`SC9`). */
  readonly tier?: CheckTier;
}

/** The cross-tool canonical root guidance file. Owned here and imported by every call
 *  site that needs it (`S5`) — including the pre-existing `conventions-doc` entry,
 *  which stops re-literalling it. */
export const AGENTS_GUIDANCE_PATH = 'AGENTS.md';

/** Accepted locations for the repo's front-door document (`G1`). */
export const README_PATHS = ['README.md'] as const;

/** Accepted locations for a lightweight architecture/structure document. The set is
 *  exactly what `harny-document` already writes or bootstraps — its step 2.3 names
 *  "`ARCHITECTURE.md` or `AGENTS.md`" — plus the common `docs/` placement, so the check
 *  can never demand a file the delegated writer would not produce (`G1`, `G4`). */
export const ARCHITECTURE_PATHS = [
  'ARCHITECTURE.md',
  AGENTS_GUIDANCE_PATH,
  'docs/architecture.md',
] as const;

/** The label the runner prints for the new family. Owned here, travels as data in
 *  `--checks` — the runner never literals it (`G7`, `SC8`). */
export const REPO_READINESS_FAMILY_LABEL = 'repo readiness';

/** Builds the fifth family's entries. Separated from `buildDoctorChecks`' manifest
 *  body so the two families' membership can never be confused at a glance, and so the
 *  family can be unit-tested without constructing the whole file. Pure (`BG-17`). */
export function buildRepoReadinessChecks(
  generators: readonly Generator[],
): readonly DoctorCheck[];
```

`buildDoctorChecks(config, generators)` keeps its exact signature and purity, and gains
one field in its return value (see § Data Models). Its existing `require` array is
**unchanged**: no entry is added to it, removed from it, or reordered within it — which
is what keeps `conventions-doc` blocking under a stale committed runner
(`intent.md` § Constraints).

The three entries `buildRepoReadinessChecks` returns, in this fixed order:

```ts
[
  {
    id: 'repo-readiness:readme',
    description: 'a README exists',
    anyOf: README_PATHS,
    remediation: 'add a README.md describing what this project is and how to run it',
    tier: 'must-have',
  },
  {
    id: 'repo-readiness:architecture',
    description: 'an architecture or structure document exists',
    anyOf: ARCHITECTURE_PATHS,
    remediation:
      "add an ARCHITECTURE.md (or an AGENTS.md section) describing this repo's components and how they fit together",
    tier: 'recommended',
  },
  // ...then one entry per distinct declared per-tool guidance path, in resolved-
  // generator order, deduped first-seen, with `undefined` filtered out:
  ...dedupePreserveOrder(
    generators
      .map((generator) => generator.guidancePath)
      .filter((guidancePath): guidancePath is string => guidancePath !== undefined),
  ).map((guidancePath) => ({
    id: `repo-readiness:agent-guidance:${guidancePath}`,
    description: `${guidancePath} or ${AGENTS_GUIDANCE_PATH} exists`,
    anyOf: [guidancePath, AGENTS_GUIDANCE_PATH],
    remediation: `add ${guidancePath} (or a root ${AGENTS_GUIDANCE_PATH}) so this tool reads project guidance`,
    tier: 'recommended',
    requires: HARNESS_GATE,
  })),
]
```

**Traces to:** G1, G2, G6, G7.

### Public API — the canonical runner, `templates/doctor/run-doctor.mjs`

Invocation surface unchanged: `node run-doctor.mjs [--checks <path-or-inline-json>]`.
Three behavioral changes, all data-driven:

```js
// 1. `emit` accepts a third outcome and keeps a fourth counter.
function emit(id, outcome, detail) {
  lines.push(`${outcome.toUpperCase()} ${id}${detail ? ` - ${detail}` : ''}`);
  if (outcome === 'ok') okCount += 1;
  else if (outcome === 'skip') skipCount += 1;
  else if (outcome === 'warn') warnCount += 1;
  else failCount += 1;
}

// 2. One presence-entry evaluator, shared by family 2 and family 3 — the same
//    single-implementation discipline `probeSatisfied` follows (RD-3). The miss branch
//    splits on the entry's own declared tier; an absent `tier` is must-have, the
//    pre-feature behavior, preserved exactly.
function evaluateEntry(entry, cwd) {
  if (!requirementMet(entry.requires, cwd)) {
    emit(entry.id, 'skip', 'requirement not met, skipping');
    return;
  }
  if (anyPathExists(entry.anyOf, cwd)) {
    emit(entry.id, 'ok');
  } else if (entry.tier === 'recommended') {
    emit(entry.id, 'warn', entry.remediation);
  } else {
    emit(entry.id, 'fail', entry.remediation);
  }
}

// 3. Five families, in fixed order. Family 3 is new; its label and its entries both
//    arrive as data (G7) — the runner literals neither.
//    1. environment       2. harness manifest (checks.require)
//    3. repo readiness (checks.repoReadiness)                  <-- NEW
//    4. spec state        5. tests (checks.commands)
for (const entry of checks.require ?? []) evaluateEntry(entry, cwd);
emitFamilyHeading(checks.repoReadinessLabel);
for (const entry of checks.repoReadiness ?? []) evaluateEntry(entry, cwd);

// Summary gains one count; the exit-code expression is untouched.
console.log(`summary: ${okCount} ok, ${skipCount} skipped, ${warnCount} warned, ${failCount} failed`);
process.exit(failCount > 0 ? 2 : 0);
```

`checks.repoReadiness ?? []` and `checks.repoReadinessLabel` are the only new reads.
Both tolerate absence, so a pre-feature `checks.json` runs unchanged (`SC9`).
**Traces to:** G1, G2, G7.

### Public API — `templates/doctor/README.md`

The canonical behavior document is amended **first**, as behavior, tool-neutrally
(`S7`), before any implementation detail:

- Behavior 1 becomes **five** families in fixed order, naming the new one and why it is
  separate from the harness manifest.
- A new behavior states the **two tiers**: a must-have item that is absent fails the run
  and makes the repo not ready; a recommended item that is absent warns and never
  changes an exit code.
- Existing behavior 4 ("a skip is reported as coverage, never as a pass") is **extended,
  not replaced**, to distinguish three non-`ok` cases: not checked (`skip`), checked and
  lacking but not blocking (`warn`), checked and blocking (`fail`).
- Existing behavior 5 (exit codes) is restated unchanged, with the explicit note that a
  warned run is a ready run.
- A new behavior states the **presence/coherence division**: the runner asserts presence
  only and never inspects a document's contents; judging whether a document says
  anything useful is the reading procedure's job, one layer up.

**Traces to:** G2, G3, G7.

### Skill interface — `.claude/skills/harny-doctor/SKILL.md`

Two steps added after its existing "read the report in full" step. Prose contract:

- **Assess coherence.** For each guidance document the runner reported present — this
  project's conventions document, its README, its architecture/structure document —
  read it and judge three elements:
  - **Purpose** — does it state what this project is and what it is for?
  - **Components** — does it name the top-level structure and what each main part does?
  - **Validation** — does it name the commands that prove a change is good (tests, lint,
    type-check, build)?
  Report each element as stated or missing, per document, by name. All three are
  **must-have for the conventions document** — the file the agent actually reads as its
  instructions — and **recommended** for the README and the architecture document.
- **Report a readiness verdict, then ask.** State "ready for SDD work" or "not ready for
  SDD work": not ready when the runner failed any must-have entry, or when the
  conventions document is missing any coherence element. Then name the specific files
  and the specific missing elements and **ask the caller whether to delegate drafting to
  `harny-document`**. Invoke `harny-document` only after an explicit yes.

Its existing guardrails are unchanged and one is added: *the hand-off is offered, never
taken unilaterally — this skill does not write files and does not decide on the human's
behalf that a gap should be filled.*

**Traces to:** G3, G4.

### Skill interface — `.claude/skills/harny-document/SKILL.md`

One additional, explicitly-bounded entry point beside the existing post-audit one:

- **Bootstrap mode** — invoked by `harny-doctor` after a human go-ahead, or directly by
  a human, for a **named** repo-level document with no feature and no `audit.md` in
  play. Inputs: the named document(s), the missing coherence element(s), and the
  repository itself as evidence. It drafts only the named documents, marks each draft
  for human review, and never touches source code, a `specs/` path, `CHANGELOG.md`, or
  any `harny-sync`/`harny-adr` hand-off.
- The existing post-audit path — its `APPROVED`/`APPROVED WITH RESERVATIONS`
  precondition, its `REJECTED` refusal, its `Shipped:` stamp, and its `harny-sync` →
  `harny-adr` → `harny-sync` chain — is unchanged and is **not reachable** from
  bootstrap mode.

**Traces to:** G5.

## Data Models

### `DoctorChecksFile` — `.sdd/doctor/checks.json`

Two additive top-level members. Serialization is unchanged:
`JSON.stringify(x, null, 2)` plus a trailing newline; key order is declaration order;
every array is emitted in a fixed order (`BG-17`, `CLI-4`, `S3`).

```ts
export interface DoctorChecksFile {
  readonly version: 1;
  readonly specs: {
    readonly dir: string;
    readonly reservedDirs: readonly string[];
    readonly schemaFiles: readonly string[];
    readonly shippedMarker: string;
    readonly approvedVerdicts: readonly string[];
  };
  readonly require: readonly DoctorCheck[];
  /** **(NEW.)** The fifth family's entries. */
  readonly repoReadiness: readonly DoctorCheck[];
  /** **(NEW.)** The label the runner prints for that family — data, never a runner
   *  literal (`G7`). */
  readonly repoReadinessLabel: string;
  readonly commands: readonly ReadinessCommand[];
}
```

**`version` stays `1`, deliberately.** A bump signals an incompatible schema, and this
change is compatible in both directions: a new runner reading an old file finds no
`repoReadiness` and contributes no lines from family 3, while every family-2 entry —
including the blocking `conventions-doc` — behaves identically; an old runner reading a
new file ignores the two unknown keys and still runs all four families it knows,
including `conventions-doc`. The worst case in either direction is the new family being
absent, never a check silently downgraded. This is exactly why `conventions-doc` was
**not** moved into the new family. **Traces to:** G1, G7.

### The fifth family's entries

| `id` | `anyOf` | Tier | `requires` gate | Serves |
|---|---|---|---|---|
| `repo-readiness:readme` | `README.md` | must-have | *(none — universal)* | G1, G2 |
| `repo-readiness:architecture` | `ARCHITECTURE.md`, `AGENTS.md`, `docs/architecture.md` | recommended | *(none — universal)* | G1 |
| `repo-readiness:agent-guidance:<path>` | `<path>`, `AGENTS.md` | recommended | `{ anyFile: ['.sdd/harness.json'] }` | G1, G6 |

`README.md` is the one must-have this family adds. The other universal must-have — a
conventions document — is already enforced, blocking, by `conventions-doc` in family 2,
and is deliberately not duplicated here. The per-tool entries are harness-gated (ADR
0020's posture): a repo with no `.sdd/harness.json` never opted into any tool, so
evaluating tool-specific expectations against it would be a finding about a choice it
never made. **Traces to:** G1, G2, G6.

### Verified per-tool root instruction files

The value each generator declares for `guidancePath`:

| Generator | `guidancePath` | Why |
|---|---|---|
| `claude-code` | `CLAUDE.md` | Its own root instruction file; this repo's `CLAUDE.md` is the worked example. |
| `cursor` | `undefined` | Cursor reads `AGENTS.md` (and `CLAUDE.md`) at the project root alongside `.cursor/rules`; `AGENTS.md` is already in every entry's `anyOf`, so a separate entry would be redundant. Verified 2026-09-14. |
| `kiro` | `.kiro/steering` | Workspace steering directory; Kiro also supports `AGENTS.md`, which the `anyOf` fallback covers. Verified 2026-09-14. |
| `github-copilot` | `.github/copilot-instructions.md` | Repository custom-instructions file. Verified 2026-09-14. |
| `codex` | `undefined` | Codex CLI loads `AGENTS.md` from global, project-root and current-directory layers; `AGENTS.md` is its native root file. Verified 2026-09-14. |

These facts inherit the standing per-tool re-verification caveat already on record as
open reservations `AL-30` (Cursor/Kiro/Copilot) and `CG-1`/`O4` (Codex) in
`specs/current/tool-generators.md`: verified against vendor documentation, never against
a live install. **The blast radius is deliberately bounded:** every entry in this row is
`recommended`, and every `anyOf` includes `AGENTS.md`, so a wrong path here degrades to
a redundant advisory entry that any repo with an `AGENTS.md` satisfies anyway — a
misleading remediation string, never a false red. **Traces to:** G6.

### Coherence elements

Judged by the skill, never by the runner (`G3`). Exactly three:

| Element | Question | Why an agent needs it | Tier (conventions doc) | Tier (README / architecture) |
|---|---|---|---|---|
| Purpose | What is this project and what is it for? | Without it, an agent infers intent from code and its inference becomes the spec. | must-have | recommended |
| Components | What are the top-level parts and what does each do? | Without it, exploration is unbounded and a change lands in the wrong module. | must-have | recommended |
| Validation | What commands prove a change is good? | Without it, an agent cannot close its own feedback loop and declares done on unverified work. | must-have | recommended |

**Traces to:** G3.

## State Changes

- **Nothing is written by the readiness check, on any outcome** — including a failed
  repo-readiness outcome. `RD-6`/`SC19` preserved verbatim. The only process state the
  runner mutates is its own exit code.
- **`npx harny init` writes additional content, not additional files.**
  `.sdd/doctor/checks.json` gains two top-level members; the generated file count is
  unchanged, so `TG-10`'s artifact arithmetic and `tests/packaging.test.ts`'s
  `EXPECTED_TEMPLATE_FILES` count are unaffected.
- **`runDoctor`'s return value is unchanged.** No `warned` field is added; see
  `intent.md` § Non-Goals on RD-R2.
- **`harny-document` bootstrap mode writes repo-level documents only** — the same set
  its post-audit path already writes (`README.md`, `AGENTS.md`/`ARCHITECTURE.md`), never
  `CHANGELOG.md` (there is no shipped change to log), never a `specs/` path, never
  source.
- **Dogfood (this repo):** regenerated `.sdd/doctor/checks.json`, updated
  `.sdd/doctor/run-doctor.mjs` (byte-identical to the template, `BG-11`), and the
  `.agents/skills/` + `templates/skills/` copies of both edited skills.

**Traces to:** G1, G2, G4, G5.

## Behavior Guarantees

1. **AR-1 — Five check families run in fixed order.** environment → harness manifest →
   repo readiness → spec state → tests. Each check produces exactly one line; no failing
   check aborts the run (`BG-2` preserved). This amends `RD-1` and invariant `I3` from
   four families to five; the ordering guarantee itself is unchanged. *(G1 · SC1)*
2. **AR-2 — Amended readiness invariant.** Ready means every check is `ok`, `skip`, or
   `warn`; not ready means at least one check is `fail`. The result stays deterministic:
   the same repo state always produces the same outcome. This amends invariant `I2` and
   is stated here so `harny-sync` archive mode carries the amendment into
   `specs/current/readiness-checks.md` rather than leaving two contradicting statements
   on disk. *(G2)*
3. **AR-3 — A must-have gap makes the repo not ready.** An entry with `tier:
   'must-have'` or no `tier` whose `anyOf` finds nothing emits `FAIL`, the runner exits
   `2`, `runDoctor` raises `HarnessError('NOT_READY')`, and the verb exits `6`. *(G2 ·
   SC2, SC5)*
4. **AR-4 — A recommended gap never changes an exit code.** An entry with `tier:
   'recommended'` whose `anyOf` finds nothing emits `WARN` naming its remediation; a run
   whose only non-`ok` outcomes are warns and skips exits `0` and returns
   `ready: true`. *(G2 · SC3)*
5. **AR-5 — Absent `tier` means must-have.** A `require` entry with no `tier` field
   behaves exactly as today. Every `checks.json` generated before this feature keeps its
   exact outcomes under the new runner, and a runner reading such a file produces no
   family-3 lines rather than erroring. *(G2 · SC9)*
6. **AR-6 — Three repo-readiness entries exist, with these ids, paths and tiers**,
   exactly as tabulated in § Data Models. *(G1 · SC2, SC3, SC6)*
7. **AR-7 — `conventions-doc` is untouched.** Its id, its position in `require`, its
   `anyOf`, its absent `tier` (hence must-have) and its failing outcome are unchanged,
   and the repo-readiness family does not duplicate it. A missing `AGENTS.md`/`CLAUDE.md`
   still fails the run and still exits `6`. *(G2 · SC5)*
8. **AR-8 — Per-tool guidance entries are derived, never enumerated.** They are computed
   from the `guidancePath` of the resolved `Generator` instances, deduped preserving
   first-seen order, with `undefined` filtered out. `src/doctor.ts` contains no tool id,
   no instruction-file path literal, and no tool count. *(G6 · SC6, SC7)*
9. **AR-9 — Every generator declares `guidancePath`.** All five implement the member as
   a compile-time-checked `string | undefined`, so a sixth generator cannot be added
   without answering the question. Declared values match the verified-facts table
   character for character. *(G6 · SC6)*
10. **AR-10 — Per-tool guidance entries are harness-gated**
    (`requires: HARNESS_GATE`), so an unscaffolded repo skips them with a notice rather
    than being measured against tools it never selected. The two universal entries are
    ungated, like `conventions-doc`. *(G1)*
11. **AR-11 — The runner hard-codes nothing new.** No document name, accepted path,
    tier value, or family label appears as a literal in `templates/doctor/
    run-doctor.mjs`; every one arrives via `--checks`, carried by the two new
    `DoctorChecksFile` members. This is the explicit non-repetition of RD-R1's mistake.
    *(G7 · SC8)*
12. **AR-12 — One presence-entry evaluator.** Families 2 and 3 are evaluated by the same
    function; the tier split exists in exactly one place. No probe kind is added and
    `probeSatisfied` remains the single probe implementation at
    `templates/shared/probes.mjs` (`RD-3`, `BG-19`, `BG-20` preserved). *(G1, G7)*
13. **AR-13 — Determinism and byte-identity hold.** `buildDoctorChecks` and
    `buildRepoReadinessChecks` are pure: identical config and generators produce a
    byte-identical `checks.json` (`BG-17`, `CLI-4`). `.sdd/doctor/run-doctor.mjs` stays
    byte-identical to `templates/doctor/run-doctor.mjs` (`BG-11`). *(G1 · SC13)*
14. **AR-14 — The summary line reports four counts** in the order `ok`, `skipped`,
    `warned`, `failed`, and a `WARN` line is textually distinct from both `SKIP` and
    `FAIL`. *(G2 · SC4)*
15. **AR-15 — The check still writes nothing, on any outcome**, including a red
    repo-readiness result (`RD-6`). *(G1 · SC15)*
16. **AR-16 — Verb and direct invocation still agree.** `npx harny doctor` and
    `node .sdd/doctor/run-doctor.mjs` evaluate the same five families and reach the same
    ready/not-ready conclusion, from one `buildDoctorChecks` implementation (`RD-7`,
    `BG-7`). *(G1)*
17. **AR-17 — Coherence is assessed by the skill, never by the runner.**
    `run-doctor.mjs` performs no content inspection of any guidance document — no grep,
    no heading match, no keyword list. The three coherence elements are judged by
    `harny-doctor` reading the files, reported per document by name, with must-have
    status for the conventions document and recommended status for the others. *(G3 ·
    SC11)*
18. **AR-18 — The hand-off is asked for, never taken unilaterally.** `harny-doctor`
    states a ready / not-ready verdict, names the specific files and missing elements,
    and invokes `harny-document` only after an explicit caller go-ahead — the same
    never-self-approve discipline the three pipeline gates enforce. Its existing
    guardrail *"Never fix what it finds — this skill reports and stops; it does not edit
    files"* survives verbatim. *(G4 · SC11)*
19. **AR-19 — `harny-document`'s bootstrap mode is bounded and marked.** It refuses to
    touch source code, any `specs/` path, `CHANGELOG.md`, or any `harny-sync`/`harny-adr`
    hand-off; every document it produces in this mode is marked as a draft for human
    review; and the post-audit path's `REJECTED` refusal and `Shipped:`-stamp ordering
    are unchanged and unreachable from bootstrap mode. *(G5 · SC12)*
20. **AR-20 — Skill parity and frontmatter limits hold.** Each edited `SKILL.md` is
    byte-identical between `.claude/skills/<id>/` (via the `.agents/skills/` bridge) and
    `templates/skills/<id>/` (`FC-11`, `BG-13`); each keeps only the six permitted
    frontmatter keys (`SL-3`) and a `description` under the cap (`SL-4`). *(G4, G5 ·
    SC13)*
21. **AR-21 — The canonical behavior document is amended first**, stating the five
    families, the two tiers, the `warn` outcome and the presence/coherence division as
    behavior, tool-neutrally (`S7`), before any implementation detail — extending
    behavior 4 rather than replacing it. *(G2, G3 · SC14)*
22. **AR-22 — Harny's own repository is its own worked example.** Running the check
    against this repository in its current state produces zero new failures and zero new
    warnings: `README.md` exists (must-have satisfied); `AGENTS.md` satisfies
    `repo-readiness:architecture`; `.sdd/harness.json` selects `claude-code` only, whose
    `CLAUDE.md` exists and whose entry `AGENTS.md` would satisfy regardless. *(G1 ·
    SC10)*
23. **AR-23 — No new dependency.** No runtime or dev dependency is added (`S4`,
    `BG-18`). *(G1)*

## Error Handling Contract

| Error Condition | Behavior | User Impact |
|---|---|---|
| `README.md` absent | `FAIL repo-readiness:readme - add a README.md describing what this project is and how to run it` | Runner exits `2`; verb exits `6`; repo reported **not ready** |
| Conventions document absent | `FAIL conventions-doc - ...`, unchanged from today | Unchanged red result; exit `6` |
| No architecture/structure document at any accepted path | `WARN repo-readiness:architecture - ...` naming the remediation | Named finding; run still ready; exit `0` |
| A selected tool's guidance file absent **and** no root `AGENTS.md` | `WARN repo-readiness:agent-guidance:<path> - ...` | Named finding; run still ready; exit `0` |
| `.sdd/harness.json` absent | Every `repo-readiness:agent-guidance:` entry reports `SKIP ... - requirement not met, skipping`; the two universal entries still evaluate | Report distinguishes "not checked" from "checked and lacking" |
| An entry declares an unrecognised `tier` value | Treated as must-have (the `=== 'recommended'` test is exact); no throw | Conservative: an unknown tier never silently downgrades a finding |
| A pre-feature `checks.json` is supplied | `checks.repoReadiness ?? []` yields no family-3 lines; families 1, 2, 4, 5 behave exactly as before | Degraded coverage, never a wrong outcome |
| A stale committed runner is spawned with new-format checks | Families 1, 2, 4, 5 run, including blocking `conventions-doc`; family 3 is silently absent | Remediation documented in `templates/doctor/README.md`: re-run `npx harny init` after upgrading harny |
| `--checks` missing, unreadable, or invalid JSON | Runner exits `1`, unchanged | Unchanged: a broken runner is never confused with a red result |
| `harny-doctor` finds a guidance document present but unreadable | Reported as a coherence finding naming the file; no throw, no write | Named finding; never a silent pass |
| Conventions document present but missing a coherence element | `harny-doctor` reports **not ready for SDD work**, naming the document and the element | Human decides; no file written without a go-ahead |
| Caller declines the `harny-document` hand-off | `harny-doctor` reports the gaps and stops | No file is written; the recommendation stands in the report |
| `harny-document` bootstrap mode invoked with a `specs/<feature>/` target | Refuses and reports why | Bootstrap mode can never be used to bypass the post-audit gate |

`HarnessError` (`src/errors.ts`) remains the only deliberately thrown error type (`S2`);

## Dependencies

- **New runtime dependencies:** none.
- **New dev dependencies:** none. (`S4`: a new dependency requires an explicit line
  here; this feature deliberately has none.)
- **Internal:** `src/doctor.ts` → `src/generators/types.ts` (the new `guidancePath`

  `vocabulary.ts`, `config.ts`, `errors.ts`. Import direction stays strictly downward;

- **Runner:** `templates/doctor/run-doctor.mjs` keeps its only import, `probeSatisfied`

## Integration Points

- **`src/init.ts` → `buildDoctorFiles`** — unchanged call site; the richer `checks.json`
  flows through with no signature change and no additional file (`CLI-8`, `TG-10`
  unaffected).
- **`src/cli.ts` → `runDoctor`** — unchanged; the `doctor` verb gains no flag and no new
  exit code.
- **All five generators** (`src/generators/{claude-code,cursor,kiro,github-copilot,
  codex}.ts`) — each gains one declarative member. No generator's rendering behavior
  changes, so `TG-3` (byte-for-byte canonical body preservation) and `TG-4` (only
  path/wrapper/model/capability differ per tool) are untouched.
- **`harny-doctor` → `harny-document`** — a new skill-to-skill hand-off, human-gated,
  referred to by skill name and never by path, matching `harny-doctor`'s existing
  guardrail on naming other skills.
- **`harny-doctor` ↔ `harny-standards`** — no duplication: `harny-standards` owns
  code-level conventions (`S1`–`S7`); `harny-doctor`'s coherence assessment covers
  project-level orientation (purpose / components / validation) and names
  `harny-standards` as the owner of the rest. A target repo needs no second conventions
  document.
- **`harny-adr`** — unchanged and deliberately not extended; see `intent.md`
  § Constraints.
- **`harny-sync` archive mode** — will merge these requirements into
  `specs/current/readiness-checks.md` (amended `RD-1`/`I3` to five families, amended
  `I2` per AR-2, the two-tier model, the new family's entries) and into
  `specs/current/tool-generators.md` (the `guidancePath` member and the verified-facts
  table), and will register any ADR this feature earns.

## Candidate ADRs

Recorded for `harny-adr` to evaluate after audit; not decided by this document.

- **A fifth check family rather than more entries in family 2** — it amends `RD-1` and
  invariant `I3`, both shipped current truth.
- **The must-have / recommended tier split and the new `warn` outcome** — it amends
  invariant `I2` and changes what "ready" means; and the decision to leave
  `conventions-doc` in family 2 rather than move it, for stale-runner safety.
- **Presence in the runner, coherence in the skill** — the division of labour that keeps
  keyword matching out of the deterministic layer.
- **`guidancePath` as a declarative `Generator` member**, continuing ADR 0011 rather
  than ADR 0014, and the use of `undefined` to mean "this tool's root file *is*
  `AGENTS.md`".
